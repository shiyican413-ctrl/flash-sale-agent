# 面试讲解稿

## 一分钟介绍

这个项目是一个基于 Spring Boot 的秒杀系统，主要模拟电商大促中的限时抢购场景。系统支持活动配置、缓存预热、用户秒杀、Redis 原子扣库存、MQ 异步下单、订单超时关闭和库存回补。为了防止高并发下数据库被打垮，我没有让秒杀请求直接访问 MySQL 扣库存，而是先用 Redis 和 Lua 脚本完成库存预扣，再通过消息队列异步创建订单。数据库层面也加了唯一索引，作为防重复下单的最后兜底。

## 面试官可能问：为什么不用数据库直接扣库存？

可以回答：

秒杀场景下瞬时请求量很高，如果所有请求都打到 MySQL，会造成行锁竞争，数据库压力很大。我的设计是活动开始前把库存预热到 Redis，秒杀时通过 Lua 脚本在 Redis 中原子扣减库存。只有抢购成功的请求才进入 MQ，由消费者异步创建订单。这样可以把大部分失败请求挡在缓存层，减少数据库压力。

## 面试官可能问：如何防止超卖？

可以回答：

我做了三层保障。第一层是 Redis Lua 脚本，库存判断和扣减在一个脚本里原子执行。第二层是 MQ 消费端的幂等处理，避免重复消息创建重复订单。第三层是数据库兜底，订单表有 `user_id + activity_id` 的唯一索引，库存更新也会带 `available_stock > 0` 条件。

## 面试官可能问：如何防止一个用户重复抢？

可以回答：

Redis 中为每个活动维护一个已抢购用户集合。Lua 脚本扣库存前先判断用户是否在集合里，如果已经存在就直接返回重复购买。抢购成功后，把用户 ID 写入集合。同时数据库订单表也有 `user_id + activity_id` 唯一索引，防止极端情况下重复落库。

## 面试官可能问：为什么要用消息队列？

可以回答：

秒杀接口要尽量短，不能在请求线程里做太多数据库操作。所以抢购成功后，我只发送一条下单消息，然后快速返回处理中。订单创建由 MQ 消费者异步完成，这样可以削峰，也能提升接口响应速度。如果消费失败，可以重试或进入死信队列，后续再补偿。

## 面试官可能问：如果 MQ 发送失败怎么办？

可以回答：

如果 Redis 扣减成功但 MQ 发送失败，需要做补偿。可以把失败记录写入本地消息表，由定时任务重试发送；如果最终确认发送失败，就回补 Redis 库存并删除用户购买标记。更稳妥的方案是使用事务消息或本地消息表，保证业务操作和消息发送最终一致。

## 面试官可能问：订单超时未支付怎么处理？

可以回答：

订单创建成功后发送一条延迟消息，比如 15 分钟后检查订单状态。如果订单仍然是待支付，就把订单改成已取消，并回补库存。为了防止重复回补，库存流水要记录回补操作，订单状态更新也要带状态条件。

## 面试官可能问：如何做限流？

可以回答：

我会做多级限流。网关层可以按 IP 限流，应用层按用户和接口限流，Redis 中记录短时间窗口内的访问次数。对于秒杀接口，还可以使用动态地址、验证码和请求签名，避免接口被提前刷。

## 面试官可能问：Agent 模块有什么意义？

可以回答：

Agent 不参与核心交易链路，因为秒杀链路需要确定性。它主要做辅助分析，比如活动上线前巡检、库存差异分析、异常订单解释和压测报告总结。它会调用系统内部工具读取活动、库存、订单、风控和日志数据，然后生成自然语言建议，帮助运营或开发更快发现问题。

## 项目难点总结

- 高并发下如何减少数据库压力
- Redis 库存和 MySQL 订单如何最终一致
- MQ 消费如何保证幂等
- 订单取消后如何正确回补库存
- 秒杀接口如何防刷
- 系统异常时如何补偿
