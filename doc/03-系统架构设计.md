# 系统架构设计

## 总体架构

```text
用户浏览器 / App
        |
        v
Nginx / 网关层
        |
        v
Spring Boot 应用
        |
        +--> Redis：活动缓存、库存、用户购买标记、限流计数
        |
        +--> RabbitMQ / RocketMQ：秒杀下单消息、订单超时消息
        |
        +--> MySQL：商品、活动、订单、用户、库存流水
        |
        +--> AI Agent 服务：巡检、分析、问答、报告生成
```

## 核心秒杀链路

1. 管理员创建商品和秒杀活动。
2. 管理员执行活动预热，将活动信息和库存写入 Redis。
3. 用户登录后查看活动列表。
4. 用户获取验证码和动态秒杀地址。
5. 用户发起秒杀请求。
6. 后端校验登录、活动时间、验证码、限流规则和动态地址。
7. Redis Lua 脚本判断库存是否充足，并校验用户是否已经购买。
8. Lua 脚本扣减 Redis 库存，写入用户购买标记。
9. 后端发送秒杀下单消息到 MQ。
10. 消费者异步创建订单，写入 MySQL。
11. 用户通过查询接口轮询秒杀结果。
12. 超时未支付订单关闭，并回补库存。

## 为什么用 Redis 扣库存

秒杀开始时，用户请求量会远大于数据库可承受的写入量。如果每个请求都直接访问 MySQL 扣库存，会导致数据库行锁竞争严重，甚至拖垮数据库。

因此系统先把活动库存预热到 Redis，通过 Redis 单线程执行 Lua 脚本完成原子扣减。只有抢购成功的请求才进入 MQ，最终异步落库。

## Lua 脚本职责

Lua 脚本需要保证以下操作原子完成：

- 判断活动库存是否大于 0
- 判断用户是否已经购买过
- 扣减库存
- 记录用户购买标记

伪代码：

```lua
local stock = tonumber(redis.call('GET', stockKey))
if stock == nil or stock <= 0 then
  return 1
end

if redis.call('SISMEMBER', userSetKey, userId) == 1 then
  return 2
end

redis.call('DECR', stockKey)
redis.call('SADD', userSetKey, userId)
return 0
```

返回值：

- `0`：成功
- `1`：库存不足
- `2`：重复购买

## MQ 削峰设计

秒杀接口不直接创建订单，而是发送下单消息：

```json
{
  "requestId": "uuid",
  "userId": 10001,
  "activityId": 20001,
  "goodsId": 30001,
  "quantity": 1,
  "createTime": "2026-05-29T10:00:00"
}
```

消费者处理时需要：

- 根据 `requestId` 做消息幂等
- 查询活动和商品有效性
- 插入订单
- 插入库存流水
- 发送订单超时关闭消息

## 防超卖设计

系统使用三层保障：

1. Redis Lua 原子扣减，绝大多数请求在缓存层完成库存判断。
2. MQ 消费者幂等处理，避免重复消息导致重复下单。
3. MySQL 唯一索引和库存条件更新兜底。

数据库兜底示例：

```sql
UPDATE seckill_stock
SET available_stock = available_stock - 1
WHERE activity_id = ?
  AND available_stock > 0;
```

## 防重复下单设计

- Redis Set 记录已成功抢购用户。
- 订单表增加唯一索引：`uk_user_activity(user_id, activity_id)`。
- MQ 消费者使用 `request_id` 做幂等记录。

## 订单状态机

```text
WAIT_PAY -> PAID
WAIT_PAY -> CANCELED
PAID -> REFUNDED
```

状态说明：

- `WAIT_PAY`：待支付
- `PAID`：已支付
- `CANCELED`：已取消
- `REFUNDED`：已退款

## 缓存 Key 设计

```text
seckill:activity:{activityId}              活动详情
seckill:stock:{activityId}                 活动库存
seckill:user:set:{activityId}              已抢购用户集合
seckill:result:{activityId}:{userId}        秒杀结果
seckill:rate:user:{userId}                  用户限流
seckill:rate:ip:{ip}                        IP 限流
seckill:path:{activityId}:{userId}          动态秒杀地址
seckill:captcha:{activityId}:{userId}       验证码
```

## 库存一致性方案

秒杀开始前：

- MySQL 是库存配置的主数据源。
- 管理员点击预热后，库存同步到 Redis。

秒杀中：

- Redis 负责实时扣减。
- MySQL 通过 MQ 异步落订单和库存流水。

秒杀后：

- 对比 Redis 剩余库存、MySQL 成功订单数和库存流水。
- 如有差异，进入人工审核或补偿任务。

## 异常补偿

- MQ 发送失败：回滚 Redis 扣减或写入失败补偿表。
- MQ 消费失败：进入重试队列，超过次数进入死信队列。
- 订单创建失败：回补 Redis 库存并移除用户购买标记。
- 支付超时：关闭订单并回补库存。

## 部署架构

本地开发可使用 Docker Compose 启动：

- MySQL
- Redis
- RabbitMQ
- Spring Boot 应用
- Nginx，可选

生产环境建议：

- 应用多实例部署
- Redis 主从或集群
- MQ 高可用部署
- MySQL 主从
- Prometheus + Grafana 监控
